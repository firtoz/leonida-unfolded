# Review public contributions

Read the repository's [contribution guidelines](../../../CONTRIBUTING.md) for the project rules and examples. Apply them to drafts as well as material about to be shared.

1. Review what will actually leave the workspace. For commits, inspect the staged names and diff, including additions, renames, binaries, fixtures, and generated files. If the index is empty while preparing a commit, inspect the intended diff and new files. For a push or PR, review every outgoing commit and its message against the intended base. For a draft issue or PR, also inspect the body, comments, links, and attachments. For Pages or a release, review the exact packaged files.
2. Check provenance in context. Original explanations of ordinary archive structures, rendering, and decals fit the project. If text or code closely follows a private trace, disassembly, or copied proprietary implementation, use a high-level description and keep the evidence private. Record the source and compatible license of reused code or assets. Route proposed protected-reader changes and publication details to the maintainer.
3. Replace private evidence with what a reader needs to reproduce the issue. Use a camera bookmark for a location, an original fixture for parser or rendering behavior, and a short sanitized message for an error. Cite a synthetic check as synthetic and keep real-game captures and detailed diagnostics local.
4. If restricted material is already in Git history or online, tell the maintainer where it is without quoting or relinking it. A later deletion commit still leaves earlier content in Git history. Leave history rewrites, publication, external posts, and takedown responses to the authorized workflow.

Report actionable findings by file, commit, or submission field. Summarize which versions or artifacts you reviewed and any evidence you could not inspect.
